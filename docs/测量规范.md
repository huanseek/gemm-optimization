# 测量规范（散热 / 电源 / 降频）

> 一句话：**不用超频，不用装监控软件。每次测之前做三件事就行。**

---

## 零、★ 先看这个真实案例（2026-10 亲历）★

同一个 `gemm_v1`（i-k-j 换序），**同一台机器、同一份代码文件**：

| 什么时候测的 | v0 i-j-k | v1 i-k-j | v1 相对 v0 |
|---|---|---|---|
| 第一次 | 2498 ms / 0.860 GFLOPS | **2052 ms / 1.046 GFLOPS** | 1.22× |
| 后来重测 | 2544 ms / 0.844 GFLOPS | **347 ms / 6.195 GFLOPS** | **7.3×** |
| 再测一遍 | 2565 ms / 0.837 GFLOPS | **334 ms / 6.433 GFLOPS** | 7.7× |

**差了 6 倍。代码一个字都没改。**

### ★ 真正的原因：**编译选项**，不是电源、不是降频

**第一次那个 `gemm.exe` 是用 `gcc -g`（不带 `-O2`）编出来的。**

—— VS Code 里那个 **▷「运行」三角按钮**，C/C++ 扩展默认就用 `gcc -g`。

**怎么查出来的（三步，全部可复现）：**

| 步 | 做法 | 结果 |
|---|---|---|
| 1 | 加 `cpu probe` 量机器状态 | 探针 **0.905**，正常值 1.03 —— **只低 12%，排除降频** |
| 2 | `objdump -h gemm.exe` 看二进制 | 发现 `.debug_info` / `.debug_line` 调试段 |
| 3 | 量各编译选项的产物大小 | `gcc -O0 -g` = **68930 B**，和目标**字节级完全相同** |

**修法**：改用 `run.cmd` / `Ctrl+Shift+B` / `F5`。
→ v1 从 1.046 变成 **6.195 GFLOPS**，加速比 1.22× → 7.3×。

现在 `gemm.c` 里有编译期自检（`__OPTIMIZE__`），**没带 `-O2` 会直接打印警告**。

### ⚠️ 留个案底：我最初的结论是**错的**

**我最早把原因写成"机器降频 / 电源模式"，还配了一套听起来很自洽的解释：**

> "v0 是访存瓶颈，所以不受降频影响；v1 是计算瓶颈，所以崩了 6 倍。"

**这个解释是错的。而且它错得很有代表性。**

因为"v0 没变、v1 崩了"这个现象，**用 `-O0` 解释也完全通** ——
v0 在 `-O0` / `-O2` 之间本来就只差 16%，v1 差 6.3 倍。
**两个完全不同的原因，预测了同一个现象。**

> ### 教训：一个能自圆其说的解释，不等于正确答案
>
> **要区分两个假设，必须做一个只改变其中一个变量的实验。**
>
> 这里的关键实验是 **`cpu probe`** —— 它把"机器快不快"这个变量**单独量了出来**。
> 探针正常 0.905，就说明问题**不在机器**，只能在别处（最后查到是编译选项）。
>
> **如果当时没加这个探针，我会一直拿着那个自洽的错解释去误导人。**

### 三条真正有用的教训

1. **数字反常时，先重测，再查代码，最后才下结论**
2. **一次只改一个变量**，并且要能说出"除了 X 之外，其他全一样"
3. **听起来合理 ≠ 正确。** 找个能区分假设的量（比如探针），别靠推理自洽

> 面试讲这一段时，**别只讲结论，要讲"我先猜错了、后来怎么推翻自己的"**。
> 那比"我一次就做对了"有说服力得多。

## 一、★ 永远不要超频 ★

原因不是"超频不好"，是**它会让你的数据失去可比性**：

- 面试时老师问"你什么频率下测的？" → 你答不上来就麻烦了
- 超频后机器更热，跑大 N 时会降频，**同一版本两次跑的差异比版本差异还大**
- **这个项目的说服力来自"同一台机器上，版本之间的相对提升"，不是绝对性能**

**所以：BIOS 别动，厂商自带的"性能模式"可以开，超频软件一律不装。**

## 二、每次测之前，做这三件事（30 秒）

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | **插上电源** | 电池模式下 CPU 频率会被系统限制 |
| 2 | **设置 → 系统 → 电源和电池 → 电源模式 → 最佳性能** | 均衡模式会让 CPU 压频率 |
| 3 | **关掉浏览器和游戏** | 后台程序会抢 cache 和内存带宽 |

**做完就跑。就这么简单。**

## 三、怎么知道有没有降频（不用装任何软件）

### 方法：同一个 N 连跑 3 次，看数字

```
N=1024  第1次: 0.799 GFLOPS
N=1024  第2次: 0.756 GFLOPS     ← 掉了 5%
N=1024  第3次: 0.701 GFLOPS     ← 又掉了 7%
```

**连续变慢 = 在降频。**

程序本身已经取"重复 N 次里最快的一次"（`best of 3`），所以轻微的降频会被自动过滤掉。

**但如果"最快的那次"也在逐轮下降** → 机器热了，等 5 分钟再跑。

### 想看得更细（可选）

- **零成本**：`Ctrl+Shift+Esc` → 性能 → CPU → 右下角有"速度 x.xx GHz"。跑测试时盯着它，如果从 4.0 掉到 2.5，就是降频了。
- **想更详细**：装 **HWiNFO64**（免费，绿色版不用安装）——但**不是必需**，别为这个花时间。

## 四、实验日志里怎么写

**只写一行，放在数据表上面：**

```
测试条件：插电 / 最佳性能模式 / 第 1 次跑
```

**就这一行。** 不要写一堆看不懂的参数，写成你看不懂的东西等于没写。

## 五、数字特别不稳定怎么办

（同一版本、同一 N，两次跑差 20% 以上）

| 可能原因 | 怎么查 |
|---|---|
| 机器热了 | 等 5 分钟，凉了再跑 |
| 后台有东西在跑 | `Ctrl+Shift+Esc` 看 CPU 占用率 |
| 没插电 | 插上 |
| 内存不够，在换页 | 任务管理器看内存占用（N=4096 要 200MB+） |

> **测不准的时候，宁可不记。记一个假数字比不记更糟。**

## 六、和 CSP / 机试无关的一句话

这套规范以后也用得上：**任何"性能"相关的东西，第一步都是控制变量。**
你面试时如果能说一句"我把电源模式和后台程序都固定了，保证版本之间可比"——这本身就是加分项。
