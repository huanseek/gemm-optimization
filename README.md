# GEMM 优化：从朴素三重循环到 SIMD / OpenMP / CUDA

**作者**：刘瑞青 ｜ 目标：华中科技大学 计算机学院（复试材料）

> **一句话结论**：同一份矩阵乘法，**只改循环顺序和访存模式**，N=2048 时**加速 18 倍**
> （0.294 → 5.292 GFLOPS）。

---

## 一、当前结果

| N | 矩阵大小 | v0 朴素 i-j-k | v1 换序 i-k-j | 加速比 |
|---:|---:|---:|---:|---:|
| 256 | 256 KB | 3.658 GFLOPS | 5.381 GFLOPS | 1.47× |
| 512 | 1 MB | 3.662 | 6.050 | 1.65× |
| 1024 | 4 MB | 0.950 | 6.480 | 6.8× |
| 2048 | 16 MB | **0.294** | **5.292** | **18.0×** |

**测试环境**：Intel Core i7-12700H（6 P 核 + 8 E 核，支持 AVX2 + FMA）· Windows 11 ·
GCC 13.2.0 `-O2` · 单精度 `float` · 每次取多次运行的最快值 · 插电 + 性能模式。

---

## 二、核心结论：加速比不是常数

把上面那张表画成两条曲线，方向完全相反：

```
v0 i-j-k:   3.66 → 3.66 → 0.95 → 0.29     ← 一路崩，掉了 12 倍
v1 i-k-j:   5.38 → 6.05 → 6.48 → 5.29     ← 基本平，几乎不变
```

| N | B 矩阵大小 | 放得进哪一级 cache | v0 的表现 |
|---:|---:|---|---:|
| 256 | 256 KB | L2（P 核 1.25 MB） | 3.66 GFLOPS |
| 512 | 1 MB | 刚好进 L2 | 3.66 |
| 1024 | 4 MB | 溢出到 L3（24 MB） | 0.95 |
| 2048 | 16 MB | L3 也快装不下 | **0.29** |

**原因：**

- **v0 慢在访存。** 内层循环访问 `B[k*N+j]`，k 每加 1 地址就跳 N 个元素。
  对 N=1024 的 float 矩阵，一跳就是 4 KB = 跨越 **64 条 cache line**，
  所以**一条 cache line 只用到 1 个数**，利用率 1/16。
- **v1 快在顺序。** 内层换成 j 循环后，`B[k*N+j]` 随 j 连续递增，
  一条 cache line（64 B）装得下 16 个 `float`，**能用满 16 次**。

> **所以：加速比不是常数，它取决于工作集大小和 cache 容量的关系。**
> **N 越大，访存优化越值钱。**

## 四、怎么编译运行

```bash
# Windows（仓库自带脚本，会自动带上 -O2）
run.cmd 1024 3        # 编译并测 N=1024，重复 3 次取最快
run.cmd 2048 1        # 大 N 时重复次数用 1（v0 单次要 58 秒）
```

```bash
# 任意平台手动编译
gcc -O2 -o gemm gemm.c
./gemm 1024 3
```

> ⚠️ **必须带 `-O2`。** 不带优化的版本 v1 会慢 6 倍。
> 程序启动时会自检并在缺少优化时打印醒目警告（用 `__OPTIMIZE__` 宏）。

## 五、测量方法（这部分和代码一样重要）

1. **正确性优先** —— 每一版先用随机抽查 64 格与直接点积对比，
   **结果不对就不报性能**（因为算错的程序跑得再快也是假数据）。
2. **机器状态指纹** —— 每次运行先跑一个纯整数依赖的探针（`cpu probe`），
   用来判断本次机器状态是否正常。**所有性能数据都和 probe 值一起记录。**
3. **多次取最快** —— `best of N`，过滤首次缺页和偶发干扰。
4. **固定环境** —— 插电 + 性能模式 + 关后台，不超频。

详细规范见 [`测量规范.md`](测量规范.md)，逐版记录见 [`实验日志.md`](实验日志.md)。

## 六、踩过的坑（全部写进了文档）

| 现象 | 根因 | 是怎么查出来的 |
|---|---|---|
| v1 只快 1.22 倍 | **VS Code 的 ▷ 运行按钮默认用 `gcc -g`，不带 `-O2`** | 先用 `cpu probe` 排除降频（只低 12%），再用 `objdump` 发现二进制里有调试段，最后比对不同编译选项的产物大小 —— `gcc -O0 -g` 得到 68930 B，与目标**字节级完全相同** |
| 同一版本两次跑差 6 倍 | 机器降频 / 后台负载 | 给程序加了 `cpu probe`，让机器状态自己报告出来 |
| N=2048 看起来像卡死 | v0 单次就要 58 秒，跑 4 遍 ≈ 4 分钟 | 加了逐版本进度行 + 大 N 自动把 `reps` 降到 1 |
