# GEMM 优化：从朴素三重循环到寄存器分块 + OpenMP

**作者**：刘瑞青 ｜ 目标：华中科技大学 计算机学院（复试材料）

> **一句话结论**：同一份矩阵乘法，N=1024 上从 **0.977 优化到 566 GFLOPS**，
> 单核到实测峰值的 **84%**，多核是 v0 的 **579 倍**。

---

## 一、当前结果（N=1024）

| 版本 | 做法 | GFLOPS | 相对 v0 |
|---|---|---:|---:|
| v0 | 朴素 i-j-k | 0.977 | 1.0× |
| v1 | 换序 i-k-j | 33.507 | 34.3× |
| v2 | 内层展开 4 路 | 33.565 | 34.4× |
| v3 | k 轴分块（kblock=128） | 50.679 | 51.9× |
| v4 | i 方向展开 4 行 | 62.320 | 63.8× |
| v5 | 寄存器分块（i-j-k，4×16，8 累加器） | 122.606 | 125.5× |
| **v6** | **v5 + OpenMP（20 线程）** | **566.260** | **579.6×** |

**测试环境**：Intel Core i7-12700H（6 P 核 + 8 E 核，AVX2 + FMA，**没有 AVX-512**）·
Windows 11 · GCC 13.2.0 `-O3 -mavx2 -mfma -fopenmp` · 单精度 `float` ·
多次取最快 · 插电 + 野兽模式 · 每次记录 `cpu probe`。

## 二、这台机器的上限（自己测的，不是查规格表）

| 项 | 值 | 探针 |
|---|---:|---|
| 单核 FMA 峰值 | **148.2 GFLOPS** | `probes/peak.c` |
| L1 读 / 写带宽 | **64 / 32 字节每周期** | `probes/port.c` |
| 单核内存带宽 | **25.5 ~ 27 GB/s** | `probes/bandwidth.c` |
| L1 容量 | **48 KB** | `probes/cache.c` |
| 访存占 v3 时间的比例 | **62%** | `probes/memshare.c` |
| P 核 / E 核单线程 | **~106 / ~50 GFLOPS** | `start /affinity` 逐核钉住 |

平台理论值：DDR5-4800 双通道 = 76.8 GB/s；6 个 P 核 × 148.2 = 889 GFLOPS。

**L2 和 L3 的容量测不出来。** 指针追逐在中间那一段得到的是缓坡而不是台阶，
现代 Intel 的 L3 是非包含式的，单核测到的容量和标称值不是一回事。这一条如实写在日志里。

## 三、每一版为什么快

| 版本 | 改了什么 | 瓶颈怎么变 | 拿到了多少 |
|---|---|---|---|
| v0 → v1 | 内层从 k 换到 j | 从"跨 N 个元素的访问"变成"顺着一行读" | 34 倍 |
| v1 → v2 | 内层展开 4 路 | `-O2` 下把编译器推上向量化；`-O3` 下编译器自己做，优势消失 | 34.3 → 34.4，等于没变 |
| v2 → v3 | k 轴分块 128 | B 的切片（0.5 MB）装进 L2 | 1.51 倍 |
| v3 → v4 | i 方向展开 4 行 | B 读一次服务 4 行，向量访存 3 → 2.25 次 | 1.19 ~ 1.38 倍 |
| v4 → v5 | C 的累加搬进寄存器 | C 的读写从每个 k 一次降到每个 k 块一次 | 1.97 倍 |
| v5 → v6 | i 循环并行 | 12 个 P 逻辑核吃满 | 4.6 倍 |

**每一个数都是实测的，每个版本在 [`docs/实验日志.md`](docs/实验日志.md) 里都有独立的
「瓶颈类型 / 证据 / 因果链」三格，以及失败记录。**

几个值得单独说的：

- **v2 是白做的。** 手动展开在 `-O2` 下值 2 倍，换了 `-O3` 之后编译器自己就向量化了，
  手动展开的收益归零（33.565 vs 33.507）。
- **v4 的 1.33 是上界，不是预测。** 按"每 8 次乘加 3 → 2.25 次访存"算，只能带来 1.33 倍；
  而访存只占 62% 的时间，所以真实预期是 1.155 倍。实测 1.19。
- **v5 打了我的脸。** 我预估 1.27 倍，实测 1.97 倍。原因是我用"写 C 单独值 21%"
  去推"把 C 的读和写一起拿掉"的收益，而这两者之间有一个我没算进去的相互作用。

## 四、升到最高那一版的思路

v5 的核心只有一句话：**让 C 的累加留在寄存器里，k 块跑完才写一次。**

```
v4 的内层：for k:  C[i][j] += a * b      → C 被读 N 次、写 N 次
v5 的内层：for k:  acc     += a * b      → 只碰寄存器
           k 块结束：C[i][j] += acc      → C 被读 N/KBLOCK 次

C 被碰的次数除以 KBLOCK = 1024 ÷ 128 = 8
```

三个块尺寸是这么定的：

| 数字 | 为什么 |
|---|---|
| i 块 4 | 4 行共用一次 B 的加载 |
| **j 块 16（两个向量）** | 4 行 × 2 向量 = **8 个累加器**。只用 4 个会卡在 FMA 延迟上，掉一半 |
| k 块 128 | 沿用 v3。C 的流量从这里开始除以 128 |

**8 个累加器是硬上限。** 试过 8 行展开（16 个累加器），编译器直接不向量化了，
退化到标量，慢 6.5 倍。也试过 12 个累加器的形状，溢出到栈，慢 40%。

## 五、和 OpenBLAS 比

同一台机器，前后脚跑，各跑四次。下表是四次的范围。

| N | 线程 | 本项目 | OpenBLAS 0.3.30 | 对比 |
|---:|---:|---:|---:|---|
| 1024 | 1 | 116.4 ~ 123.4 | 131.6 ~ 132.0 | 慢 6~12% |
| 1024 | 20 | 558.1 ~ 585.8 | 546.3 ~ 571.6 | 持平，略快 2% |
| 2048 | 1 | 111.3 | 129.1 ~ 136.9 | 慢 14~19% |
| 2048 | 20 | 687.1 | 665.2 ~ 682.8 | 持平 |

**小结，只列观察到的：**

单核差 6~12%，多核持平、略快 2%。

N 从 1024 到 2048：OpenBLAS 单核 131.6 → 136.4 往上，这边 123.4 → 111.3 往下。

BLAS 单核四次里三次落在 131.4 ~ 132.0，这边四次落在 115.5 ~ 123.4。

**没有继续追。** 差距 6~12%，而这台机器前后两次跑同一份代码能差 10%，
测量精度追不上差距了。

## 六、为什么不做 CUDA

**v0 到 v6 已经把单核和多核都走到了实测上限，CUDA 不做了。**

理由三条：

1. **数据已经够了。** 单核到峰值的 84%，多核到 12 个 P 逻辑核的饱和点。
   再往上是另一个体系结构，会开一个新坑，而复试要的是"讲清楚"，不是"更多版本"。
2. **GPU 是这块 RTX 3050 Laptop**，移动端卡，做出来的数不一定比 CPU 好看，
   花的时间却要多好几倍。
3. **时间另有去处。** 这个项目在复试材料里的任务是证明"能做深、能measure、能承认边界"，
   这三点 v6 已经证完了。

如果以后要做，路是清楚的：tiled shared memory + 分块 GEMM，
和 v5 是同一套思路，只是把"寄存器"换成"shared memory"，把"线程"换成"thread block"。

## 七、编译与运行

```bash
# Windows（仓库自带脚本，会自动带上 -O3 -mavx2 -mfma -fopenmp）
run.cmd 1024 3        # 编译并测 N=1024，重复 3 次取最快
run.cmd 2048 1        # 大 N 时重复次数用 1（v0 单次要 17 秒）
```

```bash
# 任意平台手动编译
gcc -O3 -mavx2 -mfma -fopenmp -o gemm gemm.c
./gemm 1024 3
```

> **必须带优化。** 不带优化的版本 v1 会慢 6 倍。
> 程序启动时会自检并在缺少优化时打印醒目警告（用 `__OPTIMIZE__` 宏）。

**不要用 N=2048 比版本。** 那一档工作集 48 MB，超出 24 MB 的 L3，会溢到 DRAM，
同一个程序两次能差 20%。N=1024 是 12 MB，全在 L3 里，才稳。

## 八、测量方法（这部分和代码一样重要）

1. **正确性优先** —— 每一版先用随机抽查 64 格与直接点积对比，
   **结果不对就不报性能**（算错的程序跑得再快也是假数据）。
2. **机器状态指纹** —— 每次运行前有一个纯整数依赖的探针（`cpu probe`），
   用来判断本次机器状态是否正常。**所有性能数据都和 probe 值一起记录。**
3. **多次取最快** —— `best of N`，过滤首次缺页和偶发干扰。
   同时记录 spread，spread 过大（超过 10%）的数不用。
4. **一次只动一个变量** —— 对照组和实验组只差一处，其余全部保持一致。
5. **固定环境** —— 插电 + 性能模式 + 关后台，不超频。

详细规范见 [`docs/测量规范.md`](docs/测量规范.md)，
方法论见 [`docs/怎么做自己的对照实验.md`](docs/怎么做自己的对照实验.md)，
逐版记录见 [`docs/实验日志.md`](docs/实验日志.md)。

## 九、踩过的坑（全部写进了文档）

| 现象 | 根因 | 定位方法 |
|---|---|---|
| v1 只快 1.22 倍 | VS Code 的 ▷ 运行按钮默认用 `gcc -g`，不带优化 | 先用 `cpu probe` 排除降频，再用 `objdump` 看到调试段，最后比对产物大小（68930 B 精确匹配 `-O0 -g`） |
| 同一版本两次跑差 6 倍 | 机器降频 / 后台负载 | 给程序加了 `cpu probe`，让机器状态自己报告出来 |
| N=2048 看起来像卡死 | v0 单次就要 17 秒，跑 4 遍 ≈ 1 分钟 | 加了逐版本进度行 + 大 N 自动把 `reps` 降到 1 |
| 8 路 i 展开慢 6.5 倍 | 主循环没被向量化，退化成标量 | 跑 `-fopt-info-vec-optimized`，看主循环有没有 `32 byte vectors` |
| 探针跑出来是 0 | 编译器把追逐循环整个删了 | 用 `-O0` 编；这类探针不能用 `-O2` |
| 端口探针测出 12 条/周期 | GCC 把"往连续地址写同一个值"换成批量写 | 换成"读一个写一个"（copy）才测得准 |
| 脚本里的说明文字不打印 | `echo ... -> ...` 里的 `>` 被 cmd 当成重定向 | 改成 `-^>` |

## 十、目录结构

```
gemm-optimization/
├─ README.md
├─ gemm.c                       主程序：v0~v6 各版本 kernel + 计时 + 正确性自检 + probe
├─ build.cmd                    只编译
├─ run.cmd                      编译并运行（`run.cmd 1024 3`）
├─ disasm.cmd                   导出反汇编到 asm.txt
├─ sweep.cmd                    线程数扫描（不钉核）
├─ locate.cmd                   逐个逻辑 CPU 跑，找 P / E 分界
├─ groups.cmd                   把进程钉在 P 组 / E 组 / 全部，分组对比
├─ psweep.cmd                   掩码固定，只扫线程数
│
├─ docs/
│  ├─ 实验日志.md                逐版实验记录（主文档）
│  ├─ 测量规范.md                机器状态、编译条件、散热降频的处理规范
│  └─ 怎么做自己的对照实验.md     方法论：一次只动一个变量
│
├─ probes/                      标定机器上限的探针
│  ├─ peak.c / peak.cmd          单核 FMA 峰值（148.2 GFLOPS）
│  ├─ cache.c / cache.cmd        各级 cache 容量（指针追逐，必须 -O0）
│  ├─ bandwidth.c / bandwidth.cmd 内存带宽（单核 26 GB/s）
│  ├─ port.c / port.cmd          L1 读 / 写带宽（64 / 32 字节每周期）
│  ├─ memshare.c / memshare.cmd  访存占多少时间（62%）
│  ├─ v4cost.c / v4cost.cmd      v4 形状下每一条访存流各值多少
│  └─ block_shape.c / block_shape.cmd  块形状扫描（4×16 / 6×16 / 4×24）
│
├─ exp/
│  └─ exp_alias.c / run_exp.cmd  跨度扰动的对照实验
│
└─ .vscode/                     Ctrl+Shift+B 直接出结果
```

每个 `.cmd` 都用 `cd /d "%~dp0"`，所以脚本和它要编的 `.c` 放在同一个目录就能跑。

| 想干什么 | 用哪个 |
|---|---|
| 看某一版为什么快 / 为什么慢 | `docs/实验日志.md` |
| 复现某一版的数据 | `run.cmd 1024 3` |
| 标定这台机器现在的状态 | `probes/peak.cmd`（看 8 累加器那一行能不能到 148） |
| 想验证"访存占多少" | `probes/memshare.cmd` |
| 想知道 P 核和 E 核各能干多少 | `locate.cmd` 然后 `groups.cmd` |
